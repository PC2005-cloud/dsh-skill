# 大纲扩写与补全（基于文件 + 博客元数据）

## 目标与输入输出

读用户给的**大纲文件** → 扩写成**完整文章** → 生成博客**元数据** → **写回文件**。全文要像一个人认真写的，不是 AI 批量产物。

- 一个路径：写回该路径（覆盖原大纲）。两个路径：第一个是大纲（保留），第二个写成稿。
- 路径在工作区按相对、否则按绝对；路径含糊先问，别猜，并确认是可读文本。

## 素材：大纲 + 会话上下文

会话里与该主题相关的上下文同样是素材：刚写的代码、改动的文件、运行结果、学到的概念与工具用法、踩过的坑与排查过程、关键取舍与结论。写进去才有“作者实际做过”的份量，而不是空泛复述大纲。**只取相关素材，无关或敏感的不要写**（拿不准问一句）。

写前先捞实料：报错原文（原样，别转述成“报了个错”）、命令与运行输出（关键数字）、版本/环境信息、时间线与转折点（先怀疑什么、哪个证据否定了它）、排除过的假设及依据（往往最值钱）、对照实验与复现步骤、结论与后续建议。

每个小节至少覆盖“证据 + 推理 + 落点”；只有结论没有证据＝概念空转，回清单补料或删。**叙述一律客观第三人称（严禁第一人称，见“叙述人称”）**：没有亲历过程不要写成亲身经历，用可核验事实撑起。

## 大纲里的链接必须保留

截图 URL 与官网链接是文章内容的一部分，扩写后**原样保留**：官网/文档作参考来源、截图作配图引用，就近摆放或统一收到文末“参考资料”，呈现方式不明显就按直觉摆，但 **URL 原文不能少、不能改、不能替换**。不要编造链接指向的内容（一般不读它）。交付时一句话列出保留了哪些链接。大纲只写了“github 地址”这类**占位而无 URL** 时，用可靠来源（优先本会话已核实的）补真实链接，并在交付说明里点明“这条是我补的”。

## 元数据（写在文件最前的 frontmatter）

成稿必须是 Markdown，最顶部用 `---` 包裹元数据块（category 单选，tags 用 YAML 缩进列表）：

```yaml
---
title: 标题
summary: 一句话简介
category: 分类名
tags:
  - 标签1
  - 标签2
---
```

- `title`：SEO + 吸引力。核心搜索关键词进标题，具体不空泛，中文约 **20~30 字**（≈50~60 英文字符，避免被截断）；可用数字/对比/疑问做钩子（例：“用游标分页把首页查询从 320ms 降到 210ms”），**不标题党不夸大**。
- `summary`：约 **60~150 字**，含 1~2 个核心关键词，概括主旨并点出最有价值的结论，便于检索又让人想点，但必须与正文一致。
- `category`（单选）/`tags`（多选）：写**名称**不是 id，优先读者可能检索的词，别过宽或生僻。
- 用户已给过元数据或指定分类/标签/标题 → 以用户为准，不擅自改。
- 口径一致：`summary` 同样不得出现第一人称（如“我实测下来”）。

## 分类与标签：博客接口 http://localhost:18016

公开接口无需登录，用你的 HTTP 能力请求，统一走 Python 脚本（别写死 curl）。返回 `{code,message,data}`，`code=1` 成功，分页数据在 `data.rows`。

- 现有分类：`POST /api/category/page`，体 `{"pageNum":1,"pageSize":100,"query":{"type":"ARTICLE"}}`，取 `data.rows[].name`（**必须 type=ARTICLE**）。
- 现有标签：`POST /api/tag/page`，体 `{"pageNum":1,"pageSize":100}`，取 `data.rows[].name`。
- 从现有里挑最贴切的：分类 1 个、标签可多个。
- 现有列表没有、但你认为该用时：**先把要新增的名称列给用户，等明确同意**，再 `POST /api/category`（体 `{"name":"分类名","type":"ARTICLE"}`）或 `POST /api/tag`（体 `{"name":"标签名"}`），成功后按名称写进元数据。
- **绝不**调用 `/api/article`（发布由用户手动做）；**绝不**未经确认新增分类/标签。

调用方式：Python 标准库 urllib——显式 UTF-8 编解码（不乱码）、`json` 库构造请求体（不被 shell 吃掉引号导致 400）、不受 PowerShell 受限语言与 Schannel 限制。**写成临时 `.py` 再 `python <脚本.py>`，不要 `python -c` 内联中文**；临时目录不可写就管道给 `python -`。

```python
import json, urllib.request, sys
try: sys.stdout.reconfigure(encoding="utf-8")
except Exception: pass

def post_json(url, payload):
    req = urllib.request.Request(url, data=json.dumps(payload).encode("utf-8"),
                                 headers={"Content-Type": "application/json"})
    with urllib.request.urlopen(req, timeout=20) as r:
        return json.loads(r.read().decode("utf-8"))

def rows(res):
    if res.get("code") != 1:
        print("接口未返回成功:", res); return []
    return res.get("data", {}).get("rows", []) or []

cat = post_json("http://localhost:18016/api/category/page",
                {"pageNum":1,"pageSize":100,"query":{"type":"ARTICLE"}})
tags = post_json("http://localhost:18016/api/tag/page", {"pageNum":1,"pageSize":100})
print("可用分类:", "、".join(r["name"] for r in rows(cat)))
print("可用标签:", "、".join(r["name"] for r in rows(tags)))
```

跑出两行候选池。`code≠1` 或 HTTP 400 → 先自查请求体与转义，不是服务端问题。

## 工作流

1. 明确路径并确认可读；2. `read` 读大纲；3. 只有受众/篇幅/输出路径真不明才问（最多一句）；4. 过素材清单捞实料，想清读者与重点；5. **风格选择（写前必做）**：同一条消息给 3~5 个候选风格（各一句：调性 + 适合谁），**未确认前不动笔**；人称固定为客观第三人称，不用问；6. 按所选风格、以客观第三人称把每个要点扩写成有厚度的段落；7. 去 AI 味 + 第一人称复查（正则搜一遍）；8. 生成元数据（新增分类/标签先确认）；9. `write` 写回（核对路径，别覆盖无关文件）；10. 交付：路径、风格、分类与标签，各一行，不重复贴全文。

## 写作风格（写前给用户挑）

风格管“怎么讲”；人称不用选，**固定客观第三人称、严禁第一人称**（见“叙述人称”）。给 3~5 个候选，每个一句话（风格名 + 调性 + 适合谁，可补一句好处），最推荐的排第一，末尾给出自己的推荐；用户选定后再写。**用户不按候选回答、而是直接描述需求（如“就是介绍分享软件”）时，自己归到一个口径并说明理由**，别硬拉着重选。

1. **冷静分析型**：克制客观留白，“现象→证据→推理→结论”，表格与数字支撑，少用情绪化措辞，适合排障实录与观点型文章。**作者对这类反馈最好，排障/技术类优先排第一。**
2. **踩坑复盘型**：从“遇到什么问题→怎么排查→怎么解决”推进，可用第一人称复盘的结构，但**成稿仍用第三人称、严禁“我”**。
3. **干货教程型**：步骤清楚、偏“怎么做”，适合读者照着复现。
4. **技术深挖型**：讲原理、对比与取舍，偏“为什么这么写”。
5. **轻松随笔型**：短句、日常用词、少术语。**口语化只体现在句子短和用词日常，不得出现第一人称口语**（“我踩了个坑”“真香”“强推”）。

问法示例：

> 想用哪种风格？A 冷静分析型（克制客观，证据表格支撑，适合排障实录）B 踩坑复盘型（从踩的坑讲起，适合有真实折腾过程）C 干货教程型（分步骤，读者照着能复现）D 轻松随笔型（口语化，适合更宽泛读者）。我建议 A：本文排障向，读者带问题来搜，实测证据最有说服力。你定哪个？（回 A/B/C/D 或“你定”）

## 叙述人称：一律客观第三人称（严禁第一人称）

**全文一律客观第三人称，严禁第一人称，也包括第一人称的口语化表达。** 软件介绍、工具推荐、横向对比、资料整理自不必说，排障与复盘同样按客观口径写（“连接时报错 X，排查后确认是 Y”）。不询问、不默认、不留余地；**仅当用户明确说“用第一人称写”时才破例**。

- **禁用代词**：我、我们、咱、咱们、笔者、本人、大家（作主语时）。
- **禁用第一人称口语句式**：我试了下、我踩了个坑、说实话、讲真、我这边、顺手、挺香的、真香、踩雷、强推——这类表达**删掉“我”字也不算过关**，视角本身要改写成客观陈述。
- **不写主观断言**：不用“我觉得好用/我认为值得/我的建议”，改交代出处的可核验事实（版本、体积、star 数、官方文档说明）；结论直接给（“不建议当生产备份方案”）。
- **整句改写，不是删字**：`我常连的那些库它都支持`→`日常开发常见的这些库都可以直接建连接`；`我是从 Release 列表核对的`→`数据取自 GitHub Release 产物列表`；`截至我写这篇时`→`截至 2026 年 9 月底`；`如果你的情况和我的类似`→`若日常要连的数据库种类较杂`；`我的建议是先试便携版`→`建议先从便携版试起`。
- **自查**：写完先用正则 `我|咱|咱们|笔者|本人|大家` 搜一遍，再通读找残存的第一人称口语；两者命中都整句改写。
- 交付时说明“全文客观第三人称”；出现第一人称＝返工（用户明确要求第一人称的除外）。

## 核心原则

1. **段落化（硬性）**：以完整段落为主，禁止“每条 1~2 句”的罗列式扩写。列表只允许两处：① 证据/实测结果表；② 读者要照做的命令或步骤短清单；其余罗列必须揉进段落。
   反例：`- 权限问题：报错是 not a directory，不是权限问题。`
   正例：先给报错原文，再说明权限解释不了它（`Permission denied` 与 `not a directory` 是两种不同证据），落到“挂载源被解析到了另一套文件系统”——一段完成“证据→推理→落点”。
2. **有厚度**：报错原文、数字、版本、时间线、推理转折、排除过的假设、实验设计、结论收敛过程都写出来，读者能还原“当时发生了什么”；宁长而有物，不短而空。
3. **详略得当**：重点浓墨重彩（可多段），次要一小段带过，绝不平分秋色。
4. **忠于作者**：保持用户给定的语气、受众、用途，**并严格遵守客观第三人称口径**（第一优先级）。不确定问一句。
5. **按大纲结构走**：不打乱顺序、不删要点；大纲只有要点没有实料时补事实与来源，不要靠第一人称想象填空。

## 去 AI 味（写作与复查时执行）

**词汇**：不用“首先/其次/最后、总而言之、综上所述、由此可见、不难看出、众所周知”；不用“赋能、深耕、洞察、闭环、抓手、共赢、助力、开启…之旅、共同谱写、真正做到了、让我们一起”；不用“在这个日新月异的时代、随着社会的发展、让我们携手、共创美好未来”；少用“不仅…而且”式工整递进和满篇“然而/因此/与此同时”；不用成语四字排比凑数；不用“笔者认为/我们不难发现/下面给大家介绍”这类假第三人称；不用“我试了下/说实话/真香/强推”这类第一人称口语。

**结构**：别每段都“观点→解释→例子→总结”；段落长短要有变化；开头别套万能公式（假故事、假设问、假数据），要贴内容；结尾不升华不喊口号不总结陈词，**“小结/总结”标题能不用就不用**，收束写进最后一段；别每条都加“因此/这将大大提升…”的尾巴。

**语气**：允许明确取舍与判断，但不装中立、不两头讨好，**也不靠第一人称撑态度**；可用短句、日常用词、设问；用具体细节/数字/场景代替抽象（说“上月报虚高了三成”而非“数据出现一定波动”）；允许留白。个性由“细节密度 + 明确取舍 + 数据出处”承担，该给结论就给（“不建议当生产备份方案”）。

**交付前自检**：① 还在“每条 1~2 句”罗列？→ 改段落。② 有只有结论的小节？→ 补实料。③ 有没有第一人称？正则 `我|咱|咱们|笔者|本人|大家` 搜一遍，再通读找“我试了下/说实话”这类口语残留，命中就整句改写。④ 有改残的半截句/无主语句？⑤ 连续三句机械排比？→ 打散。⑥ 连接词过密？→ 删一半。⑦ 大词空转、整段没信息？→ 补细节或删。⑧ 结尾喊口号/强行总结？→ 删。⑨ 数据交代出处了吗（版本号、Release 产物、官方文档）？→ 没有就补，或改“约/例如”。⑩ 通读像“AI 代写/秘书汇报”？→ 重写那几处。

## 守则

- 只用中文常规标点，引号用全角“”（别留英文直引号）；除非用户指定，别大量用感叹号省略号。
- 不编造用户没给的事实；缺数据用“约/例如”留余地，或直接问。
- 分类/标签优先用博客现有名称；新增必先征得同意。
- 写入前核对目标路径与盘面内容；目标在工作区外时按沙箱规则取得许可，别因一次拒绝就放弃或改写别的文件。
- 只把成稿写进文件，不写思考过程与检查项。
- 一律客观第三人称：不出现第一人称代词与第一人称口语；也不写“我在跟 AI 对话／让 AI 帮我写”这类过程叙述。
- 用户提修改后**只改被指出的问题**，其余段落保持原样。
