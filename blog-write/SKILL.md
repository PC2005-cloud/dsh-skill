# 大纲扩写与补全（基于文件 + 博客元数据）

## 目标

用户会给你一份**大纲文件**（文本文件，内容是大纲、要点或灵感）。你读取它，把内容**扩写补全成一篇完整文章**，为成稿生成博客所需的**元数据**，然后把带元数据的成稿**写回文件**。全文必须读起来像一个人认真写出来的，而不是 AI 批量生成的。

## 输入与输出

- **输入**：用户提供的一个文件路径（text）。内容即大纲/要点/灵感。若路径在当前工作区，按相对路径处理；否则按用户给的绝对路径。
- **输出**：把扩写后的完整文章（含 frontmatter 元数据）写入文件。
  - 用户只给一个路径 → **写回该路径**（把原大纲覆盖为成稿）。
  - 用户给了两个路径 → 第一个是输入大纲，第二个是输出成稿（写入第二个路径，原大纲保留）。

## 素材来源（不止大纲）

这类博文通常是用户在 agent 对话中边写代码、边学习之后总结所得。因此，**当前对话/会话里与该博文主题相关的上下文，同样是重要的素材**，包括：

- 用户（作者）刚写的代码、改动的文件、运行的结果；
- 本次学到的知识点、关键概念、工具/框架用法；
- 踩过的坑、报错、排查与解决的过程；
- 关键取舍、结论和思考。

扩写时应把这些“真实发生过的事”融入正文，让博文有细节、有“作者实际做过”的份量，而不是空泛复述大纲。**只提取与该博文主题相关的材料；无关或敏感的内容不要写进文章**（拿不准哪个算相关，就问用户一句）。

### 扩写前的素材挖掘清单（写前过一遍）

提笔前先从这个清单里把“实料”捞出来，写作时才有的写：

- 报错原文（原样的错误信息、关键行，别转述成“报了个错”）；
- 命令与运行结果（输入了什么、输出了什么、关键数字）；
- 版本/环境信息（软件版本、系统、相关配置文件内容）；
- 时间线与转折点（先怀疑了什么、哪个实验/证据否定了它、哪个转折指向了真相）；
- 排除过的假设及其排除依据（这部分往往是文章最值钱的内容）；
- 对照实验/复现步骤（怎么设计的、两组结果差异在哪里）；
- 结论与后续建议。

扩写时每个小节至少覆盖“事实/证据 + 推理过程 + 落点”三项；如果某小节只有结论、没有推理或证据，说明这一节是概念空转——回清单补料，或者直接删减。

## 大纲中的链接（截图/官网）要保留在成稿中

用户大纲里的**截图 URL 和官网链接，是文章内容的一部分，扩写后必须原样保留在成稿里**——不要因为它们被当成理解素材，就在文中悄悄消失，也不要擅自改写、删掉或替换成别的内容。

- **保留方式**：官网/文档链接可作为正文里的**参考来源/相关链接**；截图 URL 可作为**配图或插图引用**。尽量在对应段落附近出现；也可以把多个链接统一整理到文末“参考资料/参考链接”区，但**URL 原文必须保留**。
- 不要编造链接指向的内容；链接本身只是**保留展示**，通常无需你去读取或复述其内部内容（除非用户另行要求）。
- 如果某个链接的呈现形式不明显（是当正文引用、还是当图片插进来），按直觉合理摆放即可。交付时可在交付说明里一句话列出“本文保留了哪些链接”。

## 成稿的元数据格式（写在文件最前面的 frontmatter）

成稿文件必须是 Markdown，最顶部用 `---` 包裹元数据块，格式如下（category 单选、tags 用 YAML 缩进列表）：

```yaml
---
title: 标题
summary: 一句话简介
category: 分类名
tags:
  - 标签1
  - 标签2
---
```

- **`title`**：AI 根据正文生成，需同时兼顾 **SEO 与吸引力**——
  - SEO：把本文最核心的搜索关键词放进标题，具体、信息明确、不空泛；中文标题控制在约 **20~30 字**（≈50~60 个英文字符内，避免被搜索引擎截断）。
  - 吸引人：在**不失专业**的前提下，可用具体结果、场景、对比、疑问、数字做钩子（例：“用游标分页把首页查询从 320ms 降到 210ms”）；**绝不标题党、不夸大**。
- **`summary`**：AI 根据正文生成，一句话（约 **60~150 字**）——
  - SEO：包含 1~2 个核心关键词，概括全文主旨，便于搜索引擎理解内容。
  - 吸引人：提炼最有价值的结论或亮点，让读者有点击欲望；但必须与正文一致，不唬人。
- **`category` / `tags`**：写**名称**（不是 id），来源见下方接口流程。选择时优先贴合主题的**搜索关键词**（读者可能用来检索的词），而非过宽或生僻词。
- 如果用户已经给过元数据或指定了分类/标签/标题，以用户给的为准，不要擅自改。

## 分类与标签：对接博客接口（http://localhost:18016）

博客的后端接口是**公开的**（无需登录）。用你手头的联网/HTTP 能力（如 DSH 的 web 工具或终端请求）访问，**不要写死具体 curl 命令**，按下面的逻辑和接口自行请求即可。

接口返回统一为 `{ code, message, data }`（`code=1` 表示成功；分页 `data` 含 `total` 和 `rows`）。

### 1. 获取现有分类（文章分类）
- `POST http://localhost:18016/api/category/page`
- 请求体：`{"pageNum":1,"pageSize":100,"query":{"type":"ARTICLE"}}`
- 从返回的 `data.rows` 里取 `name` 字段作为**可用分类名称**。
- **注意**：文章分类必须 `type="ARTICLE"`，不要用其他类型。

### 2. 获取现有标签
- `POST http://localhost:18016/api/tag/page`
- 请求体：`{"pageNum":1,"pageSize":100}`
- 从返回的 `data.rows` 里取 `name` 字段作为**可用标签名称**。

### 3. 从现有里挑选
- 根据博文主题，**优先从上面的现有分类/标签里选**最贴切的名称，写进元数据。分类选一个，标签可选多个。

### 4. 缺失时先确认，再新增（务必遵守）
- 如果你认为这篇博文**应该用某个分类/标签，但现有列表里没有**，**不要直接新增**。先把要新增的名称列给用户，等用户**明确同意**后，才调用新增接口：
  - 新增分类：`POST http://localhost:18016/api/category`，请求体 `{"name":"分类名","type":"ARTICLE"}`
  - 新增标签：`POST http://localhost:18016/api/tag`，请求体 `{"name":"标签名"}`
- 新增成功后，用该名称（或返回里记录的 id 对映到名称）写进元数据。

### 明确不做
- **不调用文章接口发布/入库**（`/api/article` 不碰）——发布由用户手动完成。
- 绝不发未经用户确认的新增分类/标签请求。

### 调用注意事项（统一用下面这一种）

统一做法：用 **Python 脚本**通过博客接口取分类与标签。相比在 PowerShell 里直接调 .NET `HttpClient`，Python 有几个稳定的优势：

- 能显式按 **UTF-8** 编码请求体、解码响应 → 中文不会再乱码；
- 用 `json` 库构造请求体 → 不会因 shell 引号被吃掉而变成非法 JSON（避免 400）；
- Python 是独立进程，不受 PowerShell 受限语言（ConstrainedLanguage）对 .NET 类型的限制（如 `HttpClient` 不可用）——在很多 agent 沙箱里，PowerShell 跑在受限语言模式，这点很关键；
- 在 Windows 受限沙箱模式下，curl/.NET 的 HTTPS 可能因 Schannel 取不到 TLS 凭据而失败，而 Python 走自带的 OpenSSL，通常仍可正常请求本机接口。

**推荐把下面的脚本写成一个临时 `.py` 文件再运行（`python <脚本.py>`），不要用 `python -c "…"` 内联传中文/引号**——内联同样会踩 shell 转义和编码问题。若沙箱临时目录不可写，可改为把脚本内容通过 stdin 管道给 Python（`python -`），效果相同。

```python
# 只需标准库（urllib），无需安装 requests
import json, urllib.request, sys
try:
    sys.stdout.reconfigure(encoding="utf-8")   # 强制 UTF-8 输出，避免终端按 GBK 显示成乱码
except Exception:
    pass

def post_json(url, payload):
    body = json.dumps(payload).encode("utf-8")          # 请求体按 UTF-8 编码
    req = urllib.request.Request(
        url, data=body,
        headers={"Content-Type": "application/json"})
    with urllib.request.urlopen(req, timeout=20) as resp:
        return json.loads(resp.read().decode("utf-8"))  # 响应按 UTF-8 解码

def rows(result):
    if result.get("code") != 1:                          # code=1 才算成功
        print("接口未返回成功:", result)
        return []
    return result.get("data", {}).get("rows", []) or []

cat  = post_json("http://localhost:18016/api/category/page",
                 {"pageNum":1, "pageSize":100, "query":{"type":"ARTICLE"}})
tags = post_json("http://localhost:18016/api/tag/page",
                 {"pageNum":1, "pageSize":100})

print("可用分类:", "、".join(r["name"] for r in rows(cat)))
print("可用标签:", "、".join(r["name"] for r in rows(tags)))
```

运行后得到“可用分类”和“可用标签”两行，把它们作为选取元数据的候选池。

- 成功与否统一看 JSON 里的 `code == 1`，分类/标签名取 `data.rows[].name`；`code≠1` 或 HTTP 400 → 多半是请求体/转义问题，先自查，不是服务端问题。
- 全程按 UTF-8 编解码即可避免乱码；不要用按系统编码（GBK）读响应的方式。

## 工作流

1. **明确路径**：先拿到清晰的输入路径。用户没给或路径含糊，先请用户给（这是读写必需，别猜）。确认是可读文本文件。
2. **读取**：用 `read` 读取该文件内容，作为本次的大纲/要点。
3. **澄清（可选）**：只有受众/篇幅/输出路径真不明时才问，最多一句。能推断就不问。
4. **准备完毕**：综合大纲 + 相关对话素材，先过一遍“素材挖掘清单”把实料捞齐，再想清楚这篇要表达什么、读者是谁、哪些点值得展开。
5. **风格选择（写前必做）**：在动手扩写之前，**先向用户提供 3~5 种候选写作风格**（见下方“写作风格”一节），每种用一句话说明特点与适用场景，请用户挑一个；用户不选或说“你定”时，按最贴合主题/受众的候选自己定，并说明我选了哪个、为什么。**在用户明确选定（或授权自定）之前，不要开始正式扩写。**
6. **扩写**：按所选风格，综合大纲 + 实料，按“核心原则”把每个要点写成**有厚度的自然段落**（段落化，见核心原则第 1、2 条），段与段用内容本身衔接，不硬贴“首先/其次/最后”。
7. **去AI味复查**：写完初稿后，用下方清单通读一遍，命中就改；重点检查是否仍残留“每条 1~2 句”的分点罗列。
8. **生成元数据**：按上方“分类与标签”流程确定 `category`/`tags`，并生成 `title`/`summary`，组装 frontmatter。需新增分类/标签时，先列给用户确认。
9. **写入**：用 `write` 把带 frontmatter 的成稿写入目标文件（默认同一路径）。写入前确认路径正确，不要误覆盖无关文件。
10. **交付**：简短告知已写入哪个路径、用了哪种风格（若用户指定）、哪个分类和哪些标签（一行），并保留成稿内容不重复贴全文。

## 写作风格：写前先给你挑

动手扩写前，**必须先给用户一组候选风格**，让用户挑好再写。不要默认套一种风格。

### 操作方式
- 根据这篇的主题、受众和素材，**现场生成 3~5 个候选风格**（可参考下面的模板，但不必照搬、要贴合本篇文章）。
- 每个候选用**一句话**点明：风格名 + 整体调性 + 适合哪种读者/场景。可选地补一句“这样做的好处”。
- 按对当前文章最合适的排序，把最推荐的放第一，并在末尾**给出 AI 自己的推荐**（例如“我建议选 A，因为这种风格的读者搜索意图最匹配本文”）。
- 等用户选定后，再按该风格扩写。

### 候选风格模板（供参照，按文章调整措辞与取舍）
1. **冷静分析型**：克制、客观、留白。以“现象 → 证据 → 推理 → 结论”推进，多用实测表格与具体数字做支撑，刻意少用第一人称情绪，适合排障实录与观点型文章——**该作者（用户）对这类风格反馈最好，排障/技术类素材可优先放第一位**。
2. **踩坑复盘型**：以“我遇到了什么问题→怎么排查→最后怎么解决”为主线，真实感强，适合分享实战经历、带反转型叙事的文章。
3. **干货教程型**：结构清晰、步骤清楚、偏“怎么做”，适合写给别人照着做、解决具体问题的文章。
4. **技术深挖型**：带原理、对比和取舍，偏“为什么这么写”，适合看懂实现、理解本质的读者。
5. **轻松随笔型**：口语、短句、少术语，偏个人视角，适合技术之外的闲谈或给大众看的科普。

### 展示示例

> 你想用什么风格写这篇？
> A. **冷静分析型** —— 克制、客观，用“现象→证据→推理→结论”推进，实测表格支撑，适合排障实录这类题材。
> B. **踩坑复盘型** —— 从我实际遇到的坑讲起，再到排查和解决，代入感强，适合有真实折腾过程的题材。
> C. **干货教程型** —— 分步骤讲清楚每一步怎么做，读者照着就能复现，最适合《xx 落地》这类文章。
> D. **轻松随笔型** —— 口语化、少术语，读起来轻松，适合面向更宽泛的读者。
> 我建议选 A：本文是排障向，读者多半带问题来搜索；实测证据表格最有说服力。你定哪个？（回 A/B/C/D 或“你定”）

## 核心原则

1. **段落化叙述（硬性要求）**：正文以完整段落为主，禁止“每条 1~2 句”的分点罗列式扩写。每个要点写成一段有实质内容的段落——给出推理过程、具体数据、场景，段落之间用内容衔接。分点列表只允许出现在两类地方：① 证据/实测结果表（对照实验、数据对比）；② 需要读者照做的命令或步骤短清单。除此之外的罗列，扩写时必须揉进段落。
   - 反例（不合格）：`- 权限问题：报错是 not a directory，不是权限问题。`
   - 正例（合格）：先给出报错原文，再解释权限解释不了这个现象（`Permission denied` 与 `not a directory` 是两种不同证据），最后落到“挂载源被解析到了另一套文件系统”的判断上——一整段完成“证据 → 推理 → 落点”。
2. **扩写要有厚度**：每个要点都要真正展开：报错原文、数字、版本、时间线、推理的转折点、排除过的假设、实验怎么设计的、结论怎么收敛的。读者应能还原“你当时做了什么”，而不是只看到结论。宁可长而有物，不要短而空泛。
3. **详略得当**：重要的点浓墨重彩（可写成多个段落），次要的点一小段带过。绝不平分秋色、每节等长。
4. **忠于作者**：保持用户给定的语气、受众和用途。不确定可问一句。
5. **按大纲结构走**：不擅自打乱大纲顺序、不删要点；某点觉得该处理，先保留，展开时自然带过去。

## 去AI味规则（写作与复查时执行）

### 一、词汇层：这些词别用
- 结构词堆叠：首先/其次/再次/最后、总而言之、综上所述、由此可见、不难看出、众所周知。
- 官腔大词：赋能、深耕、洞察、闭环、抓手、共赢、助力、开启…之旅、共同谱写、真正做到了、让我们一起。
- 空洞口号：在这个日新月异的时代、随着社会的发展、让我们携手、共创美好未来。
- 滥用“不仅…而且”“不但…还”式工整递进，以及满篇“然而/因此/与此同时”。
- 用成语或四字排比凑数、撑场面。

### 二、结构层：打破“八股”
- 不要每段都是“观点→解释→例子→总结”四段式；允许有的段落直接讲故事、有的只有两句。
- 段落长短要有变化，别整篇齐刷刷。
- 开头别套万能公式（假故事、假设问、假数据开场），要贴合内容本身。
- 结尾不要强行升华、喊口号、做总结陈词；该停就停。
- 不要每条最后都来一句“因此/这将大大提升…”的总结尾巴。

### 三、语气层：写得像“人”
- 允许有偏好和主观判断，不装客观中立、不两头讨好。
- 适当用短句、口语、设问甚至带情绪的措辞（只要贴合作者语气）。
- 用具体细节、数字、人名、场景撑起抽象说法；宁可说“上个月报虚高了三成”，不说“数据出现一定波动”。
- 允许留白：有些地方点到即止，不必把话讲满。
- 想象你在跟一个认识的人讲话，而不是在写材料。

### 四、交付前自检（至少过一遍）
- [ ] 正文是否仍以“每条 1~2 句”的分点罗列为主？——是则改写为段落叙述，只保留证据表格与命令清单。
- [ ] 是否存在某小节只有结论、缺推理或证据？——从素材挖掘清单补实料。

## 守则
- 全文只用中文常规标点；除非用户指定，别大量用感叹号和省略号刷存在感。
- 不编造用户没给的事实；确实缺数据就用“约”“例如”留出余地，或直接问。
- 元数据里的分类/标签优先匹配博客现有名称；无新增必先征得用户同意。
- 写入前再次核对目标路径与盘面内容，避免覆盖用户未打算覆盖的文件。
- 只把成稿写进文件，不要把你的思考过程和检查项写进去。
- 不要把“我是在跟 AI 对话／让 AI 帮我写”这类过程性叙述写进文章；以作者本人的口吻呈现。
