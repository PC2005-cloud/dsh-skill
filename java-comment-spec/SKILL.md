# Java 注释规范

## 目标

写 Java 代码时，按统一标准产出四类注释：**类注释、方法注释、行注释、代码块注释**。目的是让调用方不读源码就能正确使用 API，让维护者看懂每处非常规写法背后的原因。

基线规范：《阿里巴巴 Java 开发手册》（黄山版）注释规约；Javadoc 的格式与标签遵循标准 Javadoc 规范。二者与本 skill 冲突时以本 skill 为准（典型冲突：阿里规约要求每个类必写 `@author`，本 skill 默认不写，理由见硬性规则 3）。

若项目内已有 `checkstyle.xml`、p3c-pmd 配置或团队自有规范，**以项目规范为准**，本 skill 作为缺省约定。发现冲突时按项目规范写，并说明差异。

## 何时应用

**默认时机：只要产出 Java 代码就适用。** 写注释不是独立任务，而是写代码的一部分——新建类、加方法、改字段时，注释与代码在同一次产出里一起给出，不需要用户提醒。

具体场景：

- 新建或修改 Java 类、接口、枚举、注解、异常类
- 新增或修改 `public` / `protected` 方法、抽象方法、接口方法、字段与常量
- 补写或修正既有代码的注释
- 用户说"加注释""补 Javadoc""按规范写""注释写规范点"
- 评审既有 Java 代码，判断注释是否缺失、过期、无信息量

写代码时**直接产出注释**，不要反问用户是否需要加注释，也不要把"补注释"拖成另起一轮的任务。

## 硬性规则

以下为强制项，不得违反：

1. 类、类属性、类方法一律使用 `/** */` Javadoc 格式，不得用 `// xxx` 代替。
2. 所有抽象方法（含接口中的方法）必须写 Javadoc，且包含方法功能、`@param`、`@return`、可能抛出的 `@throws`。
3. **只写能从代码或用户输入确认的信息，不编造。** 作者、日期、版本号、业务背景、流量数据这类无法推断的元信息一律不写。具体到两个标签：`@author` 与 `@since` **默认不写**，仅当项目模板要求、或用户提供了真实值时才加；类上已有的 `@author` 保持原样，不得覆盖。（阿里规约要求每个类必写 `@author`，那是团队协作场景的诉求；对个人开发与 AI 生成的代码，这两项零信息量且必然被编造或腐烂，因此本 skill 不采用。）
4. 方法内部的单行注释用 `//`，另起一行写在被注释代码**上方**；多行注释用 `/* */`，与代码对齐。不使用行尾注释。
5. 枚举类型的每个枚举项都必须注释其业务含义。
6. `@param`、`@return`、`@throws`、`@deprecated` 不得出现空描述。
7. 注释随代码同步修改：改动参数、返回值、异常或核心逻辑时，必须同步改注释。
8. **注释只描述当前代码的行为、约束与原因，不记录改动历史、新旧实现对比、需求变更过程或设计心路。** 修改既有代码时，用描述当前实现的新注释**替换**旧注释，而不是把"原来是…现在改成…"追加进去。区分标准：描述"当前代码为什么必须这样写"是合格注释；描述"代码是怎么一步步变成这样的"是开发日志。

## 修改既有代码：头号禁区（不写开发日志）

**这是 AI 改代码时最高频的问题。** 拿到一个已有注释的函数去优化、重构或改需求，很容易顺手把注释写成一篇"开发日志"——对比新旧实现、复述需求变更、解释历史包袱、讲述选型心路，动辄几百字。读代码的人只想知道**现在这段代码干什么、为什么必须这么写**，不关心它是怎么演变成今天这样的。

### 症状识别

注释里出现下列任何一种，就是开发日志：

- 对比新旧实现："这里不再使用原来的 X，改成 Y"
- 复述需求变更："新需求要求…，所以…"
- 解释历史包袱："原来的字段会导致…，这次避免了…"
- 讲设计心路："考虑到…，最终选择…"
- 技术演进史："Session 时代…，现在改成 JWT…"
- 出现时间对比词：`原来`、`以前`、`之前`、`这次`、`新需求`、`改为`、`不再`、`避免`

### 判别线

**把注释的主语从「代码曾经怎么样」换成「代码现在为什么必须这样」。**

| 内容 | 性质 | 处理 |
| --- | --- | --- |
| 机制约束，如"Feign 不继承请求头，身份必须手动搬" | 当前事实 | 保留 |
| 缺失后果，如"少这个头下游会 401，且报错点远离根因" | 当前约束 | 保留，压缩成一句 |
| 待清理状态，如"Cookie 透传已无消费者" | 当前状态 | 保留，转成带责任人和时间的 TODO |
| 演进史，如"Session 时代登录态在 HttpSession 里" | 历史 | 删除 |
| 故障复盘过程，如"cart 眼里 order 是匿名访客…" | 历史 | 删除，只留结论 |
| 选型心路，如"考虑到后续可能扩展，预留了扩展点" | 历史 | 删除 |

**不要矫枉过正。** 判定标准不是"提没提过去"，而是"这条信息对读懂当前代码有没有用"。机制约束、缺失后果、待清理状态都必须留——它们是读者踩坑的唯一提示。真正要删的是**过程**，不是**结论**。

### 规矩

1. 注释描述的是**当前代码的事实**，不是它相对上一版的差异。
2. 改代码时重写注释：与新实现冲突的旧句子**直接删掉**，不保留、不加对照。
3. 确实存在反直觉之处时，只写**与当前写法直接相关的约束**，一句讲清，不交代"以前是怎么错的"。
4. 长度红线：单条行注释不超过 2 行、40 字左右。类与方法注释没有硬性字数上限，但历史叙述一律不算"必要信息"。
5. 收尾自检：把自己写的注释里所有时间对比词挑出来，出现一个就重写一遍；再问一句——删掉这条注释，下一个读代码的人会不会踩坑？会，就压缩到只讲这个坑；不会，就删。

### 反例一：改既有函数时写成新旧对比

❌ 开发日志

```java
/**
 * 这个函数原来是按 userId 查的，查询条件里还带了一个 status 字段，
 * 但是 status 在新需求里已经不维护了，会导致查出来已经被合并掉的账号，
 * 所以这次改成用 accountId 查询。同时原来的分页逻辑保留下来，
 * 因为下游的导出功能还在用；另外原来的 SQL 是先查主表再关联，
 * 这次避免了关联查询带来的性能问题，改成单表查询后再补数据。
 */
public Account queryAccount(String accountId) {
```

✅ 只交代当前事实

```java
/**
 * 按账号 ID 查询账号。
 *
 * @param accountId 账号 ID，不能为 {@code null}
 * @return 账号信息；账号不存在时返回 {@code null}
 */
public Account queryAccount(String accountId) {
```

确有反直觉之处时，补一句与当前写法直接相关的约束即可：

```java
// 必须按 accountId 而非 userId 查询：账号合并后 userId 会指向已废弃的主账号
public Account queryAccount(String accountId) {
```

### 反例二：把有价值的说明写成技术演进史

这个案例更典型——不是全错，而是**骨架合格、三分之一的篇幅在讲故事**，最容易误判。

❌ 约 350 字，其中演进史与故障过程占三分之一；正文说"搬三样东西"但列表只有两项；待清理项没有写成 TODO

```java
/**
 * Feign 远程调用时把"当前是谁"带过去。
 *
 * <p>Feign 调用是一条全新的 HTTP 请求，不会继承原来那条请求的任何头，所以要有人手动搬。
 * 这里搬三样东西，但它们的性质完全不同：</p>
 *
 * <ul>
 *   <li><b>Cookie / token</b> —— Session 时代留下的。那时登录态在 HttpSession 里，
 *       下游要读就得把 session cookie 一起带过去。现在登录态是 JWT + 网关验签后
 *       注入的请求头，这两个已经没有任何消费者，留着只是因为删之前要先确认
 *       所有服务都不读，属于待清理项。</li>
 *   <li><b>{@link AuthConstant#MEMBER_CLAIMS_HEADER}</b> —— 现在真正决定"你是谁"的头。
 *       少了它的症状很难查：order 调 cart 取购物车时 cart 眼里 order 是个匿名访客，
 *       于是返回空车或者直接 401，而报错点离根因隔了好几个服务。</li>
 * </ul>
 */
```

✅ 约 130 字，只留当前约束与后果

```java
/**
 * Feign 请求拦截器：把当前登录用户身份透传给下游服务。
 *
 * <p>Feign 调用是全新的 HTTP 请求，不继承上游请求头，身份信息必须在此手动搬运。
 *
 * <p>必须透传 {@link AuthConstant#MEMBER_CLAIMS_HEADER}，否则下游无法识别用户，
 * 表现为返回空数据或 401，且报错点通常远离此处，排查成本高。
 *
 * <p>Cookie 与 token 透传已无消费者，仅为兼容旧登录态保留，删除前需确认下游均不读取。
 */
```

被删掉的演进史与故障过程不要留在代码里，改由 TODO 记录待办：

```java
// TODO: 确认所有下游服务不再读取后，删除 Cookie/token 透传
```

### 一句话口诀

**只留当前约束，不留演进过程。** 删时代背景、删故障复盘、删选型心路；保当前约束、保反直觉原因、保待清理项。

## 改既有文件时的顺带修复

在缺注释的类里新增方法时，只注释自己新写的那部分，这个类就永远修不好——读者看到的是一条 Javadoc 孤零零挂在裸代码中间。**同文件内能一眼确定怎么改的注释缺陷，顺手一起修掉。**

### 默认直接修

- 类、接口、枚举**完全没有注释** → 补一个保守版类注释
- 枚举项缺注释
- `@param` 名字与当前签名对不上（参数已改名或已删除）
- `@return` 写在 `void` 方法或构造器上
- 标签拼写错误（`@throw`、`@retrun`）、标签空描述
- 本次新增方法用到的字段、常量缺注释
- 本次改动的方法，其旧注释已与新实现不符

这些不用问、不用列清单，回复末尾一句话带过即可。

### 拿不准就不动，也不要编

老注释与代码实际行为对不上、又判断不了哪个是预期时：**不要猜、不要圆场、不要写一段解释**。保持原样，回复里提一句"某某方法的注释与实现对不上，我没动"就够了。

补既有代码的注释时，只写**能从代码验证的事实**：职责从类名与公开方法推断，依赖从字段推断，线程安全性从字段与注解推断。业务背景、流量数据、历史原因一律不写——你不知道，写出来就是幻觉。

```java
// ❌ 编造：这些信息不可能从代码得出
/**
 * 购物车服务。集团 2019 年推行中台战略后的核心域服务，
 * 承载全站 80% 的加购流量，日均调用 2 亿次，大促峰值 QPS 5 万。
 */

// ✅ 保守：只写从代码可证实的内容
/**
 * 购物车服务：提供购物车查询、加购与结算。
 *
 * <p>依赖 {@link CartRepository} 与 {@link InventoryClient}。
 */
```

`@author` / `@since`：默认不写。类上已有就不要动；缺失时直接省略，不要写"待补充"这类占位符，也不要用当前开发者的名字冒充原作者。

### 唯一例外

第三方组件与框架源码、自动生成的代码，一律不动。

## 语言与编码

- 注释用中文；专有名词与关键字保留英文原文（`Redis`、`MySQL`、`TCP`、`SKU`）。
- 不写"半吊子英文"：与其 `// set user name`，不如 `// 设置用户名`。
- 文件编码 UTF-8；生成文档时显式指定 `-encoding UTF-8 -charset UTF-8`。
- 同一概念用词前后一致，不要一会儿"订单号"一会儿"单号"。
- 首句避免口语化表达与引号包裹的俗称，它会被抽进摘要表；写成能独立成立的陈述。

## 一、类注释

每次生成类声明，都要在上方写类注释，回答五件事：

| 要素 | 说明 |
| --- | --- |
| 职责 | 一句话说清这个类干什么（首句，以句号结尾） |
| 场景与边界 | 什么时候用、谁调用、什么时候不该用 |
| 线程安全性 | `线程安全` / `非线程安全，需外部同步` / `不可变` |
| 状态与生命周期 | 有状态还是无状态、是否单例、是否持有连接或线程 |
| 约束与前置条件 | 依赖哪个配置、要求外部先做什么 |

不得写入：方法清单（Javadoc 会自动生成）、实现步骤、改动历史、`@author` / `@since`（默认不写）、"这是一个 XXX 类"这类空话。

下面的示例都没有 `@author` / `@since`，这是刻意的：这两项无法从代码推断，默认省略，只在项目模板要求或用户给出真实值时才补。

**业务服务类**

```java
/**
 * 订单提交服务，负责下单流程编排：校验 → 扣库存 → 落库 → 发领域事件。
 *
 * <p>本类无状态、线程安全。依赖的 {@link InventoryService} 需在容器启动时完成注册。
 *
 * <p>单次提交幂等：同一 {@code requestId} 重复提交返回同一订单号。
 */
public class OrderSubmitService {
```

**工具类（强调纯函数、无状态）**

```java
/**
 * 金额计算工具。所有方法均为静态纯函数，不修改入参，不抛运行时异常。
 *
 * <p>内部统一用 {@code long} 以「分」为单位运算，规避 {@code double} 精度问题，
 * 仅在与外部接口交互时通过 {@link #toYuan(long)} 换算。
 */
public final class MoneyUtils {
```

**枚举（类注释之外，每个枚举项都要注释）**

```java
/**
 * 订单状态。状态流转规则见 {@code OrderStateMachine}。
 */
public enum OrderStatusEnum {

    /** 待支付：已创建订单但未收到付款。 */
    UNPAID(0, "待支付"),

    /** 已支付：付款成功，等待发货。 */
    PAID(1, "已支付"),

    /** 已取消：用户主动取消或超时未支付自动关闭。 */
    CANCELED(2, "已取消");
```

**异常类（说明抛出条件与调用方应对方式）**

```java
/**
 * 订单冲突异常：同一用户存在未支付订单时抛出。
 *
 * <p>属可重试异常，调用方捕获后应引导用户先支付或取消原订单。
 */
public class OrderConflictException extends BusinessException {
```

**DTO / VO / DO（类注释写数据来源与用途，字段注释写业务含义）**

```java
/**
 * 订单列表查询出参，由 {@code OrderQueryService#listByUser} 组装，
 * 字段与前端列表页一一对应，不含金额以外的敏感信息。
 */
public class OrderVO {

    /** 订单号（业务主键，非自增 ID）。 */
    private String orderNo;

    /** 应付金额，单位：分，已扣除优惠券与积分抵扣。 */
    private Long payAmount;
```

## 二、方法注释

方法注释写**契约**，不写实现。判断标准：调用方只看注释，能否正确使用这个方法。

必须覆盖：

| 要素 | 落位 |
| --- | --- |
| 做什么（首句动词短语，第三人称） | 描述 |
| 前置条件、副作用、幂等性、并发要求 | 描述 `<p>` |
| 参数含义、单位、取值范围、能否为 `null` | `@param` |
| 返回值含义、可能为 `null` 的场景 | `@return` |
| 抛出条件（受检异常必写） | `@throws` |
| 废弃时间与替代 API | `@deprecated` |

**普通业务方法**

```java
/**
 * 根据订单号查询订单详情。
 *
 * <p>结果带 5 分钟本地缓存，缓存未命中时回源数据库，无副作用。
 *
 * @param orderNo 订单号，业务主键，不能为 {@code null} 或空串
 * @return 订单详情；订单不存在时返回 {@code null}，不返回空对象
 * @throws IllegalArgumentException 当 {@code orderNo} 为 {@code null} 或空串时抛出
 * @see OrderVO
 */
public OrderVO getByOrderNo(String orderNo) {
```

**接口方法与抽象方法**：除功能、参数、返回值、异常外，必须写清对实现方的要求。

```java
/**
 * 扣减指定 SKU 的库存。
 *
 * <p>实现方必须保证：并发安全；库存不足时不扣减任何数量（失败幂等）；
 * 在调用方事务内参与回滚。
 *
 * @param skuId 商品 SKU 标识，不能为 {@code null}
 * @param count 扣减数量，必须为正数
 * @return {@code true} 表示扣减成功；库存不足返回 {@code false}
 * @throws InventoryUnavailableException 库存服务不可用时抛出，可重试
 */
boolean deduct(Long skuId, int count);
```

**覆写方法**：用 `{@inheritDoc}`，不要复制父类注释；仅在行为有额外约定时补写差异。

```java
/** {@inheritDoc} */
@Override
public String toString() {

/**
 * {@inheritDoc}
 *
 * <p>本实现额外保证结果按创建时间倒序，并过滤已删除记录。
 */
@Override
public List<Order> listByUser(Long userId) {
```

**getter / setter**：语义与字段名完全一致时可省略；字段名说明不了业务含义时必须写。

```java
// 可省略
public String getOrderNo() {
    return orderNo;
}

// 必须写
/**
 * 获取应付金额，单位：分。已扣除优惠券与积分抵扣。
 *
 * @return 应付金额，可能为 0，不会为 {@code null}
 */
public Long getPayAmount() {
```

**构造器与静态工厂**：说明创建后能否直接使用、与构造器的差异。

## 三、行注释

行注释只回答一个问题：**为什么**。代码本身已说明"是什么"，再翻译一遍就是噪音。

命中以下任一情况，必须写行注释：

1. 魔法值、非直觉常量——这个 `3`、`0.85`、`3600` 从哪来
2. 边界条件——为什么用 `>=` 而不是 `>`
3. 非直觉写法——位运算、正则、故意留空的 `catch`
4. 绕过已知缺陷——第三方库 bug、历史兼容
5. 并发与锁——为什么加锁、为什么用 `volatile`
6. 事务边界——为什么这几步必须在同一事务内
7. 性能取舍——为什么用 `StringBuilder`、为什么提前返回
8. 业务规则——判断条件背后的产品、合规约定

写法：另起一行、写在被注释代码上方，缩进与代码对齐，一句话说完，**不超过 2 行**。

| 反例 | 问题 | 正例 |
| --- | --- | --- |
| `int timeout = 3000; // 超时3秒` | 翻译代码 | `// 支付网关 P99 为 2.1s，留 30% 余量；超过 3s 用户会重复点击` |
| `if (a > 0) { } // 判断a大于0` | 零信息量 | `// 金额为正才允许退款，负数代表已冲正` |
| `// 循环处理列表` | 翻译代码 | `// 分批 500 条，避免 IN 子句超过 MySQL max_allowed_packet` |
| `// 这里很重要` | 零信息量 | `// 必须先扣库存再落库，反过来会出现「有订单无库存」的超卖` |
| `// TODO 以后优化` | 无归属无时限 | `// TODO: 接入 Redis 缓存，降低 DB QPS` |
| `list.add(x); // 添加元素` | 翻译代码 | 直接删掉 |
| `// 原来用 List 存，现在改成 Map，因为查找更快` | 开发日志 | `// 用 Map 存：一次查询 O(1)，此处单请求要查 200+ 次` |
| `// 之前这里有个 bug，是下游没传 id 导致的，后来加了判空` | 开发日志 | `// 下游可能返回不含 id 的脏数据，必须先判空` |

## 四、代码块注释

用于给长方法划分阶段。**优先抽方法，其次才加块注释**：一段步骤代码超过 15 行，就该抽成 `private` 方法，方法名本身即是最好的块注释。块注释留给「流程编排型」方法——本身就是第 1 步调 A、第 2 步调 B 的骨架。

| 方法长度 | 做法 |
| --- | --- |
| ≤ 30 行 | 通常不需要块注释 |
| 30 ~ 80 行 | 用块注释划分阶段（阿里规约建议单方法不超过 80 行） |
| 某一段 > 15 行 | 抽成 `private` 方法 |

形式：

- 步骤序号：`// 1. 参数校验`（推荐）
- 中文步骤词：`// 第一步：参数校验`
- IDEA 折叠区：`// region 价格计算` … `// endregion`，适合 100 行以上，不嵌套超过一层

**序号风格必须全文件统一**：用了 `1.` 就全用 `1.`，不要和"第一步"混用。

要求：用动词短语概括一段而非一行；步骤标题不写实现细节；与代码同缩进；关键步骤补一句原因，同样不超过 2 行；不得用块注释注释掉代码。

```java
/**
 * 提交订单。
 *
 * <p>幂等：同一 {@code requestId} 重复调用返回同一订单号，不会重复扣库存。
 *
 * @param userId  下单用户 ID，不能为 {@code null}
 * @param request 提交请求，{@code requestId} 不能为空
 * @return 提交结果，包含订单号或售罄的 SKU
 * @throws IllegalStateException 用户已被禁用时抛出
 */
public OrderSubmitResult submit(Long userId, SubmitRequest request) {

    // 1. 参数与状态校验
    validate(request);
    userService.assertActive(userId);

    // 2. 幂等检查：命中则直接返回上次结果，避免重复下单
    OrderSubmitResult exist = idempotentStore.get(request.getRequestId());
    if (exist != null) {
        return exist;
    }

    // 3. 组装订单
    // 价格在此阶段一次性算定，后续步骤只读不写，避免被优惠券规则二次修改
    Order order = buildOrder(userId, request);

    // 4. 扣减库存；失败立即返回，不进入支付环节
    if (!inventoryService.deduct(order.getSkuId(), order.getCount())) {
        return OrderSubmitResult.outOfStock(order.getSkuId());
    }

    // 5. 落库并发事件
    // 必须与库存扣减在同一事务内，否则会出现「扣了库存但没生成订单」的不一致
    orderRepository.save(order);
    eventPublisher.publish(new OrderCreatedEvent(order.getId()));

    // 6. 写入幂等记录并返回
    idempotentStore.put(request.getRequestId(), OrderSubmitResult.success(order.getId()));
    return OrderSubmitResult.success(order.getId());
}
```

## 五、Javadoc 标签速查

| 标签 | 位置 | 要点 |
| --- | --- | --- |
| `@author` | 类/接口 | **默认不写**；项目模板要求或用户提供真实值时才加，不得编造 |
| `@version` | 类/接口 | **默认不写**，同上 |
| `@since` | 类/方法 | **默认不写**；仅在维护带版本号的对外发布 API、且版本号是真实值时才写 |
| `@param` | 方法 | 每个参数一条，顺序与签名一致；不要给参数名套 `<code>` |
| `@return` | 非 void 方法 | `void` 与构造器不写 |
| `@throws` | 方法 | 受检异常必写；`Error` 不写；不写实现相关异常 |
| `@deprecated` | 类/方法/字段 | 首句写「何时废弃 + 替代 API」，与 `@Deprecated` 注解同时使用 |
| `@see` | 任意 | 相关参考 |
| `{@link}` `{@linkplain}` | 行内 | 每个 API 名只在首次出现时加链接 |
| `{@code}` `{@literal}` | 行内 | 代码、关键字、类名、包名 |
| `{@inheritDoc}` | 覆写方法 | 继承父类或接口描述 |
| `{@value}` | 常量 | 引用常量值 |

标签顺序：描述 → `@param` → `@return` → `@throws` → `@see` → `@since` → `@deprecated`；类级别若确有 `@author`、`@version`，放在描述之后。

首句规则：首句会被抽到摘要表，必须能独立成立。方法用第三人称动词句（`返回订单号。`），类用名词短语（`订单提交服务。`）；首句以句号结尾。首句在第一个「句号 + 空白」处截断，`Prof. Knuth` 这类写法要用 `&nbsp;` 规避。

段落与列表：用 `<p>` 分段，段间空一行；`<ul>`、`<table>` 等块级元素前不要再套 `<p>`。列表条目数必须与正文表述一致（说"三样"就要有三条）。

`@date` 不是标准 Javadoc 标签，不要使用；创建时间交给版本控制。

## 六、禁止清单

- **把注释写成开发日志**：对比新旧实现、复述需求变更、解释历史包袱、讲述设计心路、交代技术演进；出现"原来的""以前""这次""新需求""改为""不再使用"等时间对比词
- **编造 `@author`、`@since`、日期、版本号**，或覆盖类上已有的 `@author`，或用当前开发者的名字冒充原作者
- **给既有代码补注释时编造业务背景、流量数据、历史原因**
- 用 `// xxx` 代替类或方法的 Javadoc
- `// 判断 a 大于 0` 这类复述代码的注释
- `// 这里很重要`、`// 处理数据` 这类零信息量的注释
- 行尾注释
- 星号框注释（`/*****`、ASCII 艺术框）
- 提交注释掉的死代码；无用则删除
- 复制父类注释到覆写方法
- `@param` / `@return` / `@throws` 空描述
- 单条行注释超过 2 行
- 待清理项只写"属于待清理项"而不写成 TODO
- 同一文件内步骤注释风格混用（`1.` 与"第一步"并存）
- 正文表述与列表条目数不符
- 与代码不一致的过期注释
- 为凑注释而给自解释的 `getFoo()` 写废话

## 七、产出前核对

交付 Java 代码前逐项检查：

1. 新增的类、接口、枚举都有类注释，写明了职责与线程安全性
2. **未编造 `@author`、`@since`、日期、版本号**；无真实值时已直接省略，没有写"待补充"这类占位符
3. 每个枚举项都有注释
4. 新增的 `public` / `protected` 方法都有方法注释，标签无空描述
5. 接口与抽象方法说明了实现方必须遵守的约束
6. 覆写方法用 `{@inheritDoc}`，未复制父类注释
7. **改既有代码时，注释已改写为描述当前实现**：无新旧对比、无需求变更叙述、无设计心路、无技术演进史；行注释均不超过 2 行
8. 机制约束、缺失后果、待清理项这些"当前有效信息"仍保留，未被误删
9. 在缺注释的文件里改代码时，已顺手补齐同文件内能一眼确定的注释缺陷；拿不准的保持原样且未编造；第三方组件与生成代码未动
10. 魔法值、位运算、正则、绕过缺陷的写法都有行注释解释原因
11. 行注释均在代码上方、缩进对齐
12. 长方法的块注释步骤风格全文件统一，段落内无超过 20 行未拆分
13. 无注释掉的死代码
14. TODO / FIXME 可追踪
15. 注释与当前代码逻辑一致，没有过期描述
